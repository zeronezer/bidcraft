# 05 · 为什么用 MinerU 解析 PDF

> 这一篇讲看起来最"没有技术含量"、实际上最容易翻车的一环：把文档读进来。

## 起点：用户上传的 PDF 是什么样的

做技术选型时，我拿真实场景里的文件看了看，发现"PDF"这个词掩盖了太多东西：

| 实际形态 | 占比（我遇到的） | 特征 |
|---|---|---|
| **扫描件** | 很高 | 整页就是一张图，无任何文字层。招标文件盖章版、图纸、历史归档件大量是这种 |
| **图文混排** | 高 | 有文字层，但关键信息在表格图片、流程图中 |
| **原生电子版** | 一部分 | 正常的文字型 PDF，用 pypdf 直接抽文本就行 |
| **伪 PDF** | 偶见 | 实际是 docx 转出来的，排版信息大量丢失 |

**如果按"PDF = 有文字层的文档"来做技术选型，第一类文件直接全军覆没**——
`pypdf` 抽出来是空的，因为那一页根本没有文字层。

这就是为什么不能只用轻量解析库。**用户上传的 PDF 很可能是扫描件，纯图片那种。**

---

## 第二个需求：页码出处

这个需求比 OCR 更隐蔽，但它决定了整个架构。

标书编制有个刚需：**正文里引用的每个数字，都要能说出它出自哪份文件、哪一页/哪一节**。

- 工期"26 个月"来自招标文件 → 要能定位
- "本标段 3 座隧道"来自指导性施组 → 要能定位
- 编制人员核对时，要能点开原文看到出处

如果一个解析器只给我纯文本，我就失去了"这句话在原文的哪个位置"这个信息。
后面所有"出处可追溯"的能力都无从谈起。

所以解析产物必须携带**结构化的位置信息**：每一段文字对应第几页、第几节、
在原始文档里的什么位置。

---

## 为什么是 MinerU

MinerU（上海人工智能实验室 OpenDataLab 出品）在几个点上正好对上：

| 需求 | MinerU 的能力 |
|---|---|
| 扫描件 OCR | 内置，不需要额外接 OCR |
| 版面还原 | 输出 Markdown，标题层级、表格、图片位置都保留 |
| **位置信息** | `content_list.json` 带 `page_idx`（页号）等结构化字段 |
| 表格 | 表格还原为 Markdown 表格，不是一堆散字 |
| 图片 | 图片单独导出并保留引用位置 |
| 大文件 | 我们做了 >200 页自动切块（单任务上限 200 页） |
| 部署 | 有云端 API，不需要自建 GPU |

最后一条对开源项目很重要：**自建 GPU 推理是巨大的使用门槛**。
用云端 API，使用者只要有 token 就能跑，不需要显卡。

对比考虑过的其他方案：

- **pypdf / pdfplumber**：快、免费、无依赖，但吃不了扫描件。**作为兜底保留**（xlsx 也是直接读，见下）。
- **自建 OCR（PaddleOCR 等）**：能解决扫描件，但版面还原要自己做，且要 GPU。工程量大一个数量级。
- **其他云端文档解析服务**：能力接近，但 MinerU 开源、可自部署（如果哪天要私有化），这一点加分。

## docx 不走 MinerU：一次被推翻又翻回来的决定

这一节的结论**改过两次**，值得完整记下来，因为它很能说明"技术选型要靠实测，不能靠直觉"。

### 第一版：docx 用 python-docx 原生解析

最自然的想法——docx 本身就是结构化的，直接读段落样式就能拿到真实标题层级，
比 OCR 一遍再猜层级精确得多。

### 第二版：推翻，docx 也走 MinerU（docx → PDF → MinerU）

实测原生解析后发现了三个硬伤：

1. **表格丢位**。原生解析出来的表格，位置信息基本丢失，落到正文里位置是错的。
2. **图片引用缺失**。图片能导出，但"这张图在第几段之后"这个信息拿不到。
3. **页码完全没有**。docx 原生没有页码概念，而我们需要页码做出处定位。

于是改成：**docx 先转 PDF（docx2pdf，走本机 Office/WPS COM），再走和 PDF 完全一样的 MinerU 流程。**
理由是"**页码出处统一 > 原生结构精度**"，好处是全系统只维护一条解析链路，
切块、页码定位、图片引用改写、出处标注全部共用一套。

### 第三版（现行）：又翻回来——docx 全部走 python-docx

第二版跑了一段时间后，问题暴露出来了：

- **docx2pdf 依赖本机的 Word 或 WPS**（走 COM 调用）。这意味着**部署环境必须装 Office 套件**，
  对一个要开源的系统来说，这是很高的使用门槛，且 COM 调用本身不稳定。
- 更关键的是：把 docx 转成 PDF 再 OCR 一遍，等于**主动丢掉了 docx 本来就有的结构信息**，
  然后再靠规则去重建标题树——绕了一圈，精度还降了。
- 实测发现原生解析的三个"硬伤"里有解：表格与图片可以用**对象级解析**原位归属
  （按 Word 文档对象顺序遍历，段落与表格、图片各归其位），不必依赖"位置信息"。

所以 **2026-09-10 的最终决策是：docx（知识库与项目文件）统一走 python-docx，不再转 PDF。**
代价是**放弃 docx 的页码出处**（PDF 仍有）——这个取舍是接受的：docx 类资料以内容参考为主，
而真正需要精确页码出处的招标文件、图纸，绝大多数本来就是 PDF。

**MinerU 只负责 PDF 与图片。**

> 现在的分工很清楚：**有样式可读的（docx）直接读样式，没有的（PDF/图片）才交给 OCR。**

### 这次反复留下的教训

第二版"统一走 MinerU"在当时看是"简化架构"的好决定——一条链路比两条好维护。
但它把**部署门槛**（要装 Office）和**信息损失**（结构被拍平）这两笔隐性成本，
换成了"少维护一条链路"这笔显性收益。

**隐性成本在决策当时是看不见的，只有跑起来才会浮出来。**
这也是为什么这个项目的解析路线改了三版——不是犹豫，是实测在纠正直觉。

## 其他文件类型

不是所有文件都值得走 MinerU。成本敏感的地方直接读更划算：

| 类型 | 处理 | 理由 |
|---|---|---|
| PDF / 扫描件 / 图片 | MinerU | 需要 OCR 与版面还原（PDF 无样式可读） |
| **docx（全部场景）** | **python-docx 原生解析** | 有真实样式可读，不必绕 PDF；且不依赖本机 Office |
| **xlsx / xls** | openpyxl / xlrd 直读 | **表格数据必须数值精确**，OCR 出来会失真 |
| 图片图纸 | MinerU | 内置 OCR |

最后一行特别说明：工程量清单这类表格，走 OCR 是灾难——
"1,234.56" 变成 "l,234.56" 这种错误在报价场景里是致命的。
所以 Excel 一律直接读。

## 工程上的坑（真实踩过）

### ① 单任务 200 页上限

大文件必须切块：按页切成多份分别提交，再合并结果。切块逻辑要注意
别把一张跨页表格切断。

### ② 同文件重复解析

同一份招标文件被反复上传（改个文件名、从不同入口上传）是很常见的。
按内容 MD5 做缓存：**同一份文件永远只解析一次**。省时间也省配额。

### ③ Token 会过期

MinerU 的 token 是 JWT，有有效期。过期后所有解析静默失败。
所以 `scripts/check_env.py` 会解析 JWT 的 `exp` 字段，提前预警
（剩不到 7 天就警告，已过期直接报错并告诉你去哪续期）。
