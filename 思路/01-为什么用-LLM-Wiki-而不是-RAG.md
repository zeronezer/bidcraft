# 01 · 为什么用 LLM-Wiki 而不是 RAG

> 这是整个项目最早、也最重要的一个技术选择。它决定了知识库长什么样、检索怎么做、生成时上下文从哪来。

## 起点：一个很自然的想法

做知识库的第一反应几乎都是 RAG：

```
文档 → 切片 → 向量化 → 存向量库
问题 → 向量化 → 相似度检索 → Top-K 片段 → 塞进 prompt
```

这条路成熟、有大量现成方案、社区验证充分。我一开始也是按这个思路立项的，
`.env` 里甚至预留了 embedding 模型和向量维度配置。

但真正开始设计"AI 怎么写出一章施组"的时候，发现对不上。

---

## 为什么对不上

### 问题一：施组不是"问答"，是"照章办事"

RAG 的隐含假设是：用户有一个问题，答案散落在文档某几段里，检索出那几段就够了。

但编制施组不是这样。当我要写"2.3 隧道超前地质预报"这一节时，我需要的不是"文档里关于地质预报最相似的 5 个片段"，
我需要的是：

- **这一节应该怎么写**（先写什么、后写什么、详略怎么分配）
- **有哪些典型表格**（预报手段一览表？频率表？）
- **有哪些典型图**（预报流程图？孔位布置图？）
- **有哪些数字**（预报距离、孔数、频率）
- **适用范围**（什么情况下用 TSP，什么情况下用地质雷达）

这些是**结构化的编写知识**，不是一堆文本片段。把它切成 512 token 的块再靠相似度捞回来，
捞回来的是"文本"而不是"知识"。

### 问题二：切片的边界恰好切在最不该切的地方

我们做过实测。一份历史施组里，"超前地质预报"这一节的完整结构是：

```
超前地质预报
├─ 预报目的与依据
├─ 预报手段（TSP / 地质雷达 / 超前钻探 / 瞬变电磁）
│   ├─ 各手段原理与适用条件
│   ├─ 各手段实施方法
│   └─ 各手段成果形式
├─ 预报频率与段落划分
├─ 预报成果的反馈与施工调整
└─ 组织机构与职责
```

固定长度切片之后，"TSP 的适用范围"和"地质雷达的适用范围"被切到了不同的块里，
而且块与块的边界完全取决于字符数，跟章节结构毫无关系。检索召回了三块，
但缺了"频率与段落划分"那一块——因为那一块单独看没有很高的相似度。

**结果就是：模型拿到了一堆相关知识，但拿不到完整的写法。**

### 问题三：施组编制极度依赖"怎么写"，而不只是"写什么"

这是最本质的一条。

RAG 解决的是"写什么"（事实性知识）。但施组编制里，"怎么写"的权重远大于"写什么"：

- 一个"施工组织安排"章节，专业内容谁都知道，难的是**怎么把这个项目的具体情况组织成一段有说服力的文字**
- 一篇历史施组的价值，很多时候不在于它写了什么数字，而在于**它的行文习惯、章节展开方式、详略取舍**

这些是**风格与方法论层面的知识**，切碎了就没了。

---

## 换了什么：LLM-Wiki

核心思路很简单：

> **不要在生成时去"检索文本"，而要在解析时就把知识整理成"条目"，生成时让模型读条目做判断。**

具体做法：

### 1. 历史施组 → 知识页（不是切片，是提炼）

一份历史施组进来，先按标题结构切章建树，然后**逐章调一次 LLM 提炼**，产出一条结构化的"知识页"：

```json
{
  "title": "隧道工程 > 超前地质预报",
  "chapter_type": "施工方案",
  "tags": ["隧道"],
  "content": {
    "method": "先讲预报目的与依据，再按手段分述…",
    "key_points": ["…"],
    "tables": [{"name": "超前地质预报手段一览表", "columns": [...], "sample": [...]}],
    "images": [{"name": "超前地质预报工艺流程图", "caption": "…"}],
    "usage": "适用于隧道超前地质预报类章节，尤其需要说明多种手段组合时"
  },
  "source_location": "第 3 章 3.2 节",
  "ref_text": "（该章节的完整原文，供行文风格参考）"
}
```

注意几个关键点：

- **`method` 是"怎么写"** —— 提炼出这一节的展开方式，这是 RAG 拿不到的东西
- **`tables` / `images` 是清单** —— 不是图本身，而是"这里该有什么表/图"的提示
- **`usage` 是使用方式** —— 决定它什么时候该被引用（详见 [02](02-如何让-AI-精准命中知识.md)）
- **`ref_text` 是完整原文** —— 需要风格参考时，取完整原文而不是切片

### 2. 项目文件 → 章节索引（不是切片，是索引 + 完整原文）

项目自己上传的招标文件、指导性施组也一样不切片：

- 解析时：每一章调一次 LLM，生成 **`章节全路径标题 + 概要 + 适用范围`** 作为索引
- 使用时：AI **看索引选章节**，选中后取该章节的**完整原文**（不截断、不切片）

这个思路借的是 **skill 的思路**：先给模型一份目录和"这节讲什么"的说明，
让模型自己判断"我要写这个章节，应该看哪几节"，然后给完整的。

### 3. 工艺工法 → 一工法一条概况

工法文档更简单：一篇工法一条"名称 + 概况 + 适用范围"，用时 AI 选，选中后**整篇注入**。

---

## 效果差异

| | RAG 切片 | LLM-Wiki |
|---|---|---|
| 知识单位 | 固定长度文本块 | 结构化条目（含"怎么写"） |
| 检索方式 | 向量相似度 | AI 读索引/使用方式做判断 |
| 上下文质量 | 相关但不完整、边界随机 | 完整且结构对应章节 |
| 可追溯性 | 知道来自哪个文件，不知道来自哪一节 | 精确到"某文件 · 某章节" |
| 成本 | 需要 embedding + 向量库运维 | 解析时多花 LLM 调用，无额外基础设施 |
| 可审计 | 相似度分数，人看不懂 | 每条都有出处，人能核对 |

最后一项其实很重要：**做标书的人必须能核对来源**。向量相似度 0.83 对编制人员毫无意义，
"这条写法来自《XX 项目施组》第 3.2 节"才有意义。

---

## 代价是什么

诚实地说，LLM-Wiki 不是没有代价：

1. **解析成本更高**。一份 500 页的历史施组，切片入库几乎是免费的；逐章提炼要几百次 LLM 调用。
   所以做了并发（20 并发）和 MD5 缓存（同文件不重复解析）。
2. **解析质量决定上限**。如果提炼出来的知识页质量差，后面全差。这也是为什么提炼 prompt 改了很多轮，
   还做了"两轮提取 + 补漏 + 未匹配 block 兜底"。
3. **知识库扩容不是即时的**。新加一份历史施组，要等提炼跑完才能用（几百页约十几分钟）。
4. **放弃了"模糊联想"能力**。RAG 有时能捞到"字面不像但语义相关"的内容，章节索引做不到——
   索引没写进概要的东西就找不到。这一点靠"概要写全一点"来补偿。

**这些代价我认为是值得的**，因为换来的是上下文质量。而在"生成几十万字专业文档"这个场景下，
上下文质量基本等于输出质量。
