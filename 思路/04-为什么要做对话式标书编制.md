# 04 · 为什么要做对话式标书编制

> 这一篇不讲技术，讲产品形态。但它可能是整个项目里最"对"的一个决定。

## 先看两种形态

**形态 A：流水线式**

```
[开始编制] → 解析中… → 目录生成中… → 确认目录 → 思路生成中… → 确认思路 → 正文生成中… → 完成
```

按钮驱动，一步一步走。每步的产出用弹窗或页面展示，用户点"确认"进入下一步。

**形态 B：对话式**

```
你：帮我把第三章重写一下，突出隧道超前地质预报
AI：（调工具 → 生成 → 正文流式写入编辑器）第三章已重写，主要补充了 TSP 与地质雷达的组合方案

你：工期那几个数字统一成 26 个月
AI：（查事实表 → 找出不一致处 → 逐处修正）共修正 7 处
```

我们最终选的是 **B，但保留了 A 的骨架**。

---

## 为什么是 B

### 理由一：编制本来就是"边想边改"，不是一条直线

真实的编标过程是什么样的？

> 写到第三章，发现第二章的工期数字和这里对不上 → 回去改
> 写到隧道部分，想起来有个新工法该用上 → 补进去
> 通读一遍，觉得重难点分析太单薄 → 重写
> 领导说"这块要突出我们的技术优势" → 再调

**它从来不是"一次走完 8 个步骤"，而是"反复回到某处修改"。**

流水线形态（A）隐含的假设是"每步做完就可以往前走，不用回头"。这个假设不成立。
所以 A 形态必然会出现一种尴尬：用户在一个"已完成"的步骤里发现要改，
却找不到回去改的入口，只能重新跑一遍流程。

对话式天然适合这件事——**"回到某处修改"就是再说一句话而已**。

### 理由二：用户不需要学一套界面语言

流水线形态下，用户要学的是：这个按钮干什么、那个抽屉在哪、这一步的产出在哪看、
怎么回到上一步。每个功能都是一次学习成本。

对话形态下，用户只需要会打字。**他用做这件事本来的说法说话就行**：

- "第三章重写"（而不是：找到第三章节点 → 右键 → 选择"重新生成" → 确认）
- "工期改成 26 个月"（而不是：打开事实抽屉 → 找到总工期 → 编辑 → 保存 → 全量重新检查）
- "目录里加一节冬季施工"（而不是：定位到父节点 → 点"添加子节点" → 输入标题 → 保存）

尤其对工程行业用户——**他们不是软件用户，他们是工程师**。
少一个要学的按钮，就多一分愿意用。

### 理由三：意图和操作之间隔着一次翻译，而翻译会出错

流水线形态下，用户脑子里想的是"我要让第三章更突出隧道"，
但界面上能点的只有"重新生成第三章"。于是用户点了，得到一版和上一版差不多的内容——
因为**他的真实意图没能传达出去**。

对话式形态下，这句话原样传给了模型。模型知道你是要"突出隧道"，
于是它会调整思路、选取不同的素材。

> **能表达意图的界面，比只能表达操作的界面，上限高得多。**

### 理由四：有些需求本来就不该有按钮

"把全文里所有'施工工期'统一成'总工期'"——这个需求真实存在，
但你要为它做一个按钮吗？那"把'项目经理部'统一成'项目管理机构'"呢？

这类需求无穷无尽，做成按钮是灾难：界面会变成几百个按钮的垃圾场。

而在对话里，这就是一句话的事。

---

## "简约但不简单"体现在哪

对话式最大的风险是：**看起来很简单，实际什么都做不了**——变成一个只会说漂亮话的聊天框。

所以"简单"是留给用户的界面，"不简单"是藏在下面的东西。具体做了四件事：

### ① 模型自主决策，不做关键字拦截

早期版本试过"识别关键词决定要不要调工具"（比如看到"生成"就判断要生成）。
很快就砍掉了——因为**用户永远不会按你设想的关键词说话**。

现在的做法是让模型自己判断这一轮要不要用工具、用哪些工具：

```
用户消息 → 预判：这轮需要工具吗？
   ├─ 不需要 → 无工具直接流式输出（快，逐字上屏）
   └─ 需要   → 带工具调用，缓冲不上屏，避免"说一半改主意"
```

**分流本身也是模型判断的，不是关键字匹配。**

### ② 真流式，不是假流式

工具调用的解析是真流式——模型边吐 `tool_calls` 增量，系统边解析，
解析出来立刻执行，不用等整个响应结束。

对话回复也支持**中途停止**，且已生成的部分照常落库，不会白跑。

### ③ 执行核验：防止"假装做完了"

这是最关键的一条。大模型有个坏习惯：**它会在没真正执行的情况下声称"已完成"**。

> 用户：把第三章改成侧重隧道
> AI：好的，我已经重写了第三章，主要调整了……（实际上根本没调工具）

为了让"对话式"真的可用，做了三层防护：

1. **定稿核验**：每轮结束前必跑一次判定——如果回复里声称"已生成/已写入/已修改"，
   但本轮**没有对应的工具成功记录**背书，就否决这个回复，强制下一轮走带工具路径。
2. **剥除伪造痕迹**：模型有时会自己编造"[该轮实际执行工具：write_chapter ✓]"这种标记来蒙混过关，
   系统会主动剥除这类伪造文本。
3. **历史不注入工具标记**：给模型的历史消息里不带工具调用标注，
   防止它模仿历史格式来伪造。

还有个小细节：工具返回的错误信息里会带上**真实的节点清单**。
比如模型传了个不存在的 `node_id`，工具不返回"错误"，而是返回"当前项目实际节点如下：…"，
模型下一步就能自我修正，不需要用户重新说一遍。

### ④ 追问建议由模型决定

对话结束后给 0~3 条"接下来你可能想做"的建议。这些建议是模型根据**项目当前状态**
自主生成的，不是预设的固定话术。

比如目录刚生成完，它会建议"确认目录后生成编写思路"；
正文写了一半，它会建议"继续生成剩余章节"或"检查已完成部分的数字一致性"。

---

## 骨架还是保留了

虽然交互是对话式，但**编制的主干流程仍然是状态机**（用 LangGraph 编排）：

```
生成目录 → 生成编写思路 → （逐章生成正文）
```

理由：

- 主干流程的**顺序是确定的**，用状态机编排可以精确控制、可以断点恢复
  （进程重启后能从 MySQL 检查点接着跑）
- 中间产物需要**落库和展示**（目录树、思路），不适合只存在对话流里
- **用户随时可以用对话介入任何环节**，但流程本身不依赖对话驱动

所以最终形态是：

> **状态机管主干，对话管一切旁支和修改。**

这不是"对话式取代了流水线"，而是"流水线变成地基，对话是用户实际操作的界面"。

---

## 代价

- **不确定性**：对话形态下，用户可能不知道该说什么。所以需要引导——空状态提示、
  追问建议、工具执行过程可见（模型调了什么工具、拿到什么结果，都折叠在回复里可展开）。
- **调试更难**：同样的输入不保证同样的工具调用路径。所以把**工具执行轨迹完整记录下来**
  并展示给用户，出问题时有据可查。
- **成本更高**：对话链路每次都要带工具 schema，token 消耗高于纯按钮触发。
