# 06 · 如何保障生成准确性与降低幻觉

> **这一篇要先说清一个前提：不可能做到 100% 正确。**
> 目标不是"消除幻觉"，而是"把人工核对的工作量压到最低"。

## 先对齐目标

如果目标是"生成的内容全部正确，人不用看"，那这个项目不该存在——
AI 写几十万字专业文档，在可预见的未来都不可能达到这个标准。

但真实需求其实不是这个。真实需求是：

> **让人工从"逐字核对几十万字"，变成"扫一遍、改几处"。**

这个目标是可以达到的。而且衡量方式很明确：**打开生成的正文，需要动手改的地方有多少。**

下面所有措施都服务于这一个指标。

---

## 一、把事实从正文里拆出来单独管

这是所有措施里最重要的一条。

### 为什么

同一份施组里，"总工期"这个数字可能会出现在十几个地方。如果让模型每次都从原文里"读"这个数字，
那么十几个地方就可能出现十几个版本——26 个月、780 天、2026 年 3 月至 2028 年 4 月……

**这不是幻觉，这是"每次重新理解"必然导致的不一致。**

### 怎么做

`global_fact` 表把这类数字**抽出来单独存**：

| 字段 | 作用 |
|---|---|
| `fact_key` / `value` / `unit` | 事实本身（如 `总工期` = `26` `个月`） |
| `source_file` / `source_location` | **出处**（哪份文件、哪一节/哪一页） |
| `confidence` | 置信度 |
| `applicable_lots` | 适用范围（全线通用 / 某个标段） |
| `category` | 分类（工期 / 数量 / 资源 / 重难点…） |
| `status` / `edited` / `version` | 状态、是否人工改过、版本号 |

生成正文时，**全部事实作为权威数据注入**，模型的指令是：数字必须来自事实表或项目文件原文。

### 人工可改，且改动不会被覆盖

事实表是**可见、可编辑**的（前端"全局事实"抽屉）。

你改过的条目（`edited=1`）在后续重新抽取时**会被保留**，不会被 AI 覆盖回去。
数值发生变化时，旧版本标记为 `expired`，版本号 +1——**历史可追溯，改动可回滚**。

---

## 二、明确的冲突裁决链

当不同来源的数字打架时，模型需要一个明确的优先级，否则它会随机选一个。

```
本项目文件原文  >  本项目事实表  >  历史知识页 / 工法
```

同时上下文注入的优先级是另一条链（谁的话更该听）：

```
本次用户特别要求  >  用户经验偏好  >  项目文件原文  >  事实表  >  知识页 / 工法
```

**注意第一链的第一名是"文件原文"而不是"事实表"**——因为事实表本身是从文件抽出来的，
如果两者冲突，说明抽取可能有误，此时原文更可信。

这条裁决链写进了 `WRITER_SYSTEM` 的硬规则里，不是靠模型自己拿捏。

---

## 三、没依据就标 `[待补充]`，不许编

这是降幻觉最有效的一条硬规则：

> **所有数字必须来自「本项目事实」或「本项目文件原文」；两者都找不到的数值一律标注 `[待补充]`，
> 禁止借用历史知识页/历史原文里的数值。**

设计意图是**把"幻觉"转化成"待办事项"**。

- 模型编一个数字 → 你无法察觉，直到出事
- 模型标 `[待补充]` → 你一眼看到，去查一次，填上

**宁可留一个显眼的空，也不要填一个看不出问题的错。**

而且 `[待补充]` 在编辑器里是**可编辑的底色标记**（不是装饰性样式），
你的工作流就变成了"搜索 `[待补充]` → 逐个填"，而不是"通读全文找错误"。

---

## 四、"给风格，不给数据"——历史资料的使用边界

历史施组是最好的写作范本，但也是最危险的幻觉来源——**里面的数字全是别的项目的**。

所以对历史资料的处理是**分层使用**：

| 可以借鉴 | 严禁照搬 |
|---|---|
| 行文结构、组织顺序 | 项目名、标段号 |
| 专业措辞、通用工艺描述 | 里程桩号、日期工期 |
| 通用质量/安全/环保措施 | 工程量与数量、造价 |
| 通用管理要求 | 人员机械台数、工点名称、单位指标 |

**一句话：不依赖具体项目的文字可以借鉴，一切项目特定且可量化的内容严禁照搬。**

这也解释了为什么正文生成时只给知识页的 `ref_text`（原文）而不给 `method`（编制方式）——
详见 [03](03-上下文的取舍.md)：给了结构，模型就会连结构里的历史数字一起搬。

---

## 五、生成之后：让"用了什么"可见

前面的措施都是"生成时"的约束。但人不可能完全信任一个黑箱，所以还要解决"生成后"的问题。

正文落库时，同时记录一份**取材摘要**（`used`）：

```json
{
  "experiences": [{"id": 12, "title": "…"}],
  "knowledge_pages": [{"id": 317, "title": "隧道工程 > 超前地质预报"}],
  "file_snippets": [{"file": "招标文件.pdf", "section": "第三章 评标办法"}],
  "methods": [{"id": 8, "name": "超前地质预报施工工法"}],
  "fact_count": 23
}
```

编辑器里可以点开"取材来源"，**看到这一章的每条素材原文**。

价值在于：

- 觉得某段写得不对 → 直接查是什么素材导致的 → 针对性修正
- 看到某个来源不该被引用 → 下次就能发现是匹配逻辑的问题
- 核对时不用通读，**只查关键段落引自哪里**

> **可解释性是信任的前提。用户敢用生成结果，是因为他能随时查证。**

---

## 六、把"确定性"的部分全部交给代码

模型不擅长的事，不要勉强它。这个项目里凡是能确定计算/判断的，都不给模型：

| 环节 | 交给代码 |
|---|---|
| 事实去重 | 按 `(category, fact_key)` 归并，取高置信度，程序做 |
| 事实版本管理 | 值未变跳过，值变则旧行 expired + version+1，程序做 |
| 标段过滤 | 按 `applicable_lots` 精确匹配，程序做，不靠模型记得 |
| 父子章节去重 | 同选时只留父节点，程序做 |
| 评分类章节过滤 | 正则剔除"评标/须知/前言/致谢"类章节，程序做 |
| 表格行级裁剪 | 多标段整表按本标段词表裁行，程序做 |
| 序号→ID 映射 | 见 [02](02-如何让-AI-精准命中知识.md)，程序做 |

### 一个具体的例子：评分项

招标文件的评分办法按"评分项名称 / 权重 / 评分标准 / 数据来源"结构化提取后，
**程序会做覆盖完整性检查与分值总和核对**——因为评分项漏一条，可能导致直接废标。

**这类校验绝不能交给模型"自觉"。** 模型会说"我已核对完毕，合计 100 分"，
而实际上它可能漏了一条 5 分的项。程序算一遍，1 秒钟的事。

---

## 七、对话链路的防伪造（单独说）

正文生成的幻觉是"编内容"，对话链路的幻觉是**"谎称已完成"**——后者更致命，
因为它会让人以为事情做好了而不再检查。

三层防护（详见 [04](04-为什么要做对话式标书编制.md)）：

1. **定稿核验**：声称"已生成/已写入"必须有本轮真实工具成功记录背书，否则否决重做
2. **剥除伪造痕迹**：模型自己编的"[已执行工具 ✓]"标记会被主动剥除
3. **防模仿**：历史消息不注入工具标注，避免模型照着格式伪造

另外，工具遇到错误时**返回真实数据而不是报错**。比如模型传了个不存在的章节 ID，
工具会返回"当前项目实际节点如下：…"，模型下一步就能自我修正——
**把错误变成可自愈的信息，而不是让用户重说一遍。**

---

## 八、还有哪些措施

- **低温度**：抽取类任务用 `temperature=0.1`，正文生成 `0.4`。抽取要稳定，写作要变化。
- **结构化校验**：所有抽取结果落库前过一遍程序规整——类别白名单、去重、格式清洗。
- **重试**：限流/断连/5xx 指数退避重试（最多 5 次，基数 3s + 随机抖动）。
- **正文可回退**：重写时旧稿存入 `prev_content`，随时可还原。
- **失败不阻塞**：单路取材失败只记日志，不回退整章生成。

---

## 诚实的边界

**这套机制解决不了什么：**

- **模型理解错误**。它可能把"桥面铺装"理解成"桥面防水层"，写得完全跑题。这类错误只能靠人工审。
- **专业判断分歧**。某个方案是否合理，模型给的答案可能和资深工程师不一致——这是判断题，不是知识题。
- **长文档的一致性衰减**。整本几百页的一致性，靠逐章生成是保证不了的，
  需要最后的通读环节（这也是为什么"质检智能体"在 roadmap 上）。
- **原文本身有错**。如果招标文件里就有矛盾，模型会忠实地把矛盾抄下来。

**但可以确定的是：** 用了这些措施之后，人工核对的工作量会明显下降——
不是从 100% 降到 0%，而是从"逐字读几十万字"降到"查关键数字 + 审专业判断"。

**在标书编制这个场景里，这个降幅已经足够有价值了。**
